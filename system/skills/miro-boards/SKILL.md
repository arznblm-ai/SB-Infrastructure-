# Miro Boards — пайплайн работы с бордами

### [[2026-08-04]]

Скилл для создания презентабельных Miro-бордов (процессы, методологии, архитектуры) и их правки. Выведен из практики 2026-08-04 (борд методологии стрима «Продакшн» консалтинг-хаба).

---

## 0. Каналы доступа (в порядке приоритета)

1. **MCP `miro`** (`https://mcp.miro.com/`, OAuth, user-конфиг `~/.claude.json`). Рабочие инструменты: `canvas_get_canvas_composer_skill` (спека SVG-DSL, один раз за сессию) → `board_create` → `canvas_create_from_svg` / `canvas_read_as_svg` / `canvas_update_from_svg`. Проверка: `claude mcp list`.
   ⚠️ Старые `layout_get_dsl` / `layout_create` / `layout_read` / `layout_update` помечены deprecated (2026-08-29) — не использовать, миграция на canvas-инструменты завершена.
2. **REST API v2 (запасной, живёт всегда)** — токен `MIRO_TOKEN` в `~/.config/second-brain/miro.env`. База `https://api.miro.com/v2/boards/{board_id}/…`, board_id из URL борда с `%3D` вместо `=`. Ходить **через curl** (питоновский urllib на маке падает по SSL-сертификатам).

**Когда переключаться на REST:** ошибка MCP «This tool is not yet available to your organization / staged rollout» — это серверный фичефлаг Miro, ретраи бесполезны. `board_list_items` при этом может работать — им можно читать.

## 1. Пайплайн создания борда

### Шаг 1: контент сначала в vault
Борд — визуализация, не источник истины. Сначала структурированный markdown-файл в vault (по naming convention), потом борд. Каждый раздел файла = будущий фрейм. В файл после сборки — ссылка на борд; при правках синхронизировать оба.

### Шаг 2: выбрать визуальный формат под задачу
- **Процесс с ролями и AI** → service blueprint: горизонтальные дорожки (lanes) × этапы-колонки. Канонические дорожки: Клиент → Люди → AI-агенты → Боль → Эффект, между «клиентом» и внутренними — «линия видимости» (тонкая серая полоса с подписью).
- **Архитектура / стек** → слои сверху вниз (кто говорит с кем), оркестратор — визуальный центр, связи стрелками с подписями.
- **Roadmap / этапность** → цепочка блоков со стрелками слева направо.
- Один фрейм = одна идея. Фреймы нумеровать («01 · …», «02 · …»).

### Шаг 2.5: раскладка фреймов на борде (колоночная сетка, дефолт)
Эталон — борд «Гермес · карта скиллов и роудмэп» (2026-08-29). Правило Антона: **двигаемся не вниз — слева направо по смыслу.**
- **Дефолт — одна горизонтальная лента**: все фреймы в один ряд, верхние края на одной линии, порядок = смысловой порядок истории. Первый фрейм — «00 · Обложка и легенда».
- **Смысловые блоки идут слева направо** — каждый крупный раздел (тема) занимает свою вертикальную колонку; колонка появляется только когда у блока есть детализация.
- **Детализация блока — вниз, в его колонку**: всё, что раскрывает один смысловой блок (подсхемы, онбординг, примеры), кладётся отдельными фреймами строго под главным фреймом этого блока, друг под другом. Не размазывать детали одного блока по разным колонкам.
- Читается так: горизонтальный проход по верхнему ряду = вся история на верхнем уровне; спуск вниз по колонке = погружение в один блок.
- Геометрия: у всех фреймов одной колонки один X (левый край выровнен), вертикальный зазор между фреймами колонки одинаковый (~80–120px), горизонтальный зазор между колонками одинаковый и заметно больше вертикального (~150–250px) — колонки должны визуально читаться как группы.
- Ширины фреймов внутри колонки могут отличаться, но верхние (заглавные) фреймы всех колонок выровнены по одному верхнему Y.
- Нумерация фреймов — по смысловому порядку истории, а не по геометрии: колонка может нести «02», «04» под «01», это нормально.
- Отступать от этой сетки — только если формат диктует иное (например, один гигантский service blueprint на весь борд).

### Шаг 3: дизайн-правила (из гайдов NN/g Service Blueprints + Miro Diagram Design 101)
- **3–6 дорожек максимум**, ширина колонок и отступы одинаковые по всему борду (единая сетка = «сделано профессионально»).
- **Словарь цветов: не больше 4–5, каждый цвет = одна роль без исключений.** Проверенный набор: графит #2D2D2D структура/люди · синий #4262FF AI/автоматизация · оранжевый #F2994A боль as-is · зелёный #27AE60 эффект/to-be · красный #EB5757 риск/граница. Зафиксировать легенду на обложке.
- **Шрифт: рабочий размер 24, минимум 18.** Мелкий кегль (13–16) нечитаем на показе — проверено на живом фидбэке. Текст в плашках — по центру (`align=center valign=middle`).
- **Шейпы, не стикеры**, если борд для показа наружу: у shape точные hex-цвета и рамки, у стикеров — ограниченная палитра и «черновой» вид.
- Читаемость проверять на 20–25% зума: если разваливается — борд не готов.
- Стрелки подписывать (caption), связи по смыслу красить в цвет источника.

### Шаг 4: сборка
1. `canvas_get_canvas_composer_skill` — один раз за сессию, спека SVG-DSL в контексте.
2. `board_create` (имя ≤60 символов) — только с подтверждения пользователя.
3. Спланировать геометрию заранее по колоночной сетке из шага 2.5: фреймы — как `<g data-frame>` с абсолютной позицией, **дети внутри фрейма — в относительных координатах от его top-left угла** и должны целиком помещаться в границы фрейма. Держать запас по краям ~100px.
4. Один `canvas_create_from_svg` со всем SVG-документом: все фреймы, элементы и коннекторы в одном вызове. Проверено 2026-08-29: 89 элементов одним вызовом без сбоев. Канбан/таблицы — `foreignObject` с `data-type="kanban"`.
5. Из `result_svg` забрать `data-miro-id` элементов — они понадобятся для правок.

### Шаг 5: верификация (обязательно, отчёту сервера не верить)
- `canvas_read_as_svg` или `board_list_items` (или REST `GET /items` с пагинацией) → посчитать элементы по фреймам против плана, проверить дубли по текстам.
- **Не верить отчёту `canvas_create_from_svg` о failed/created** — истина только в фактическом чтении борда.
- После верификации — ссылку на борд в vault-файл и в трекер задачи.

## 2. Пайплайн правок

- Точечные правки: `canvas_update_from_svg` — **патч-семантика по `data-miro-id`**. В патч-SVG включать только изменяемые элементы с их `data-miro-id` (из `result_svg` создания или из свежего `canvas_read_as_svg`); не упомянутые элементы не трогаются.
- Удаление элемента — тот же `canvas_update_from_svg` с атрибутом `data-deleted="true"` на элементе.
- Перед правками — свежий `canvas_read_as_svg` нужного участка: получить актуальные `data-miro-id` и текущее состояние (пользователь мог менять борд руками).
- **Пользователь может править борд руками параллельно** — не перезаписывать его правки: перед структурными изменениями перечитать состояние; новые крупные блоки добавлять отдельным фреймом рядом, а не пересборкой существующего.
- **Порядок и состав фреймов — решает Антон (правило 2026-08-29).** Переставил фреймы — порядок НЕ восстанавливать; вместо этого обновить нумерацию в заголовках («01 · …») под новую структуру: номера следуют смысловому порядку чтения (колонки слева направо, внутри колонки сверху вниз). Удалил блок/фрейм — НЕ возвращать его в следующих версиях; в vault-файле пометить блок удалённым (контент можно оставить в файле как историю). После каждой своей правки борда сверять фактический порядок фреймов чтением и чинить только нумерацию.
- **Сдвиг существующих фреймов — только REST** `PATCH /frames/{id}` `{"position":{x,y}}` (центр, relativeTo canvas_center): `canvas_update_from_svg` молча игнорирует новый transform у `<g data-miro-id>` — отвечает success, фрейм не двигается (проверено 2026-08-29). Дети едут вместе с фреймом.
- **Патч тела textArea через canvas_update не работает**: `<br/>` уезжает на борд literal-текстом. Лечение — пересоздать (новый элемент без id + `data-deleted="true"` старого в одном вызове).
- REST-правки: `PATCH /shapes/{id}` (`style.fontSize`, `style.textAlign`, `data.content`), `PATCH /texts/{id}`. Массовые проходы — скриптом с паузой ~0.2с между запросами. Токен в python-скрипт: `set -a; source ~/.config/second-brain/miro.env; set +a` (без `set -a` переменная не экспортируется в subprocess).

## 3. Известные грабли Miro API

1. **REST bulk-create — атомарные чанки по 20**: валится целиком, если невалиден хоть один элемент. Частая причина — shape с высотой < ~12px (тонкие линии делать h=12).
2. **Сервер может врать при частичном сбое**: отчёт о created/failed может показывать чужие ID. После любого сбоя — фактическая сверка (`canvas_read_as_svg` / `board_list_items`) и зачистка дублей (`canvas_update_from_svg` с `data-deleted="true"`).
3. **REST `parent=` со ссылкой на существующий фрейм по URL может падать (HTTP 400)** — вместо этого таргетить фрейм через `?moveToWidget=<frame_id>` в miro_url и не указывать parent.
4. **Коннекторы внутри одного SVG-документа** ссылаются на элементы того же документа; для связей с уже существующими элементами борда — их `data-miro-id` из `canvas_read_as_svg` (или REST с полными ID).
5. **TEXT-элементы, созданные через MCP, могут не патчиться по REST** (internal error 3.0000) — лечится пересозданием: `POST /texts` с теми же content/position/parent → `DELETE` старого.
6. MCP-инструменты могут отвалиться фичефлагом посреди сессии — см. секцию 0, переключение на REST. Старые `layout_*` deprecated — на них не откатываться.
7. **Ручное масштабирование фрейма в UI (за угол) масштабирует детей вместе с fontSize** и может оставить фрейм в битом состоянии: `PATCH geometry` падает с «Child item cannot be placed outside the bounds of its parent» даже у ПУСТОГО фрейма (проверено 2026-08-29). Не откатывать арифметикой по частям — удалить фрейм целиком (REST `DELETE /frames/{id}`) и пересоздать из исходного SVG. Исходник всегда есть в vault-файле — поэтому «контент сначала в vault» не формальность.
8. **Пересозданный фрейм может не встать по авторским координатам** (placement engine двигает при коллизиях) — после `canvas_create_from_svg` проверить позицию и допинать REST'ом.
9. **Создание новых фреймов через canvas_update/create может сдвинуть соседние фреймы** (collision avoidance) — после добавления фрейма верифицировать позиции ВСЕХ фреймов, не только нового.

## 4. Ограничения

- `board_create` и структурные пересборки — с подтверждения Антона; его ручные правки на борде не перезаписывать.
- Устаревшие борды не удалять — пометить «(устарел, можно удалить)» в vault, удаляет Антон.
- Контент борда всегда зеркалить в vault-файл (источник истины — файл).
- Секреты (MIRO_TOKEN) — только в `~/.config/second-brain/`, не в vault.
