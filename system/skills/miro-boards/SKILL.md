# Miro Boards — пайплайн работы с бордами

Скилл для создания презентабельных Miro-бордов (процессы, методологии, архитектуры) и их правки. Выведен из практики 2026-08-04 (борд методологии стрима «Продакшн» консалтинг-хаба).

---

## 0. Каналы доступа (в порядке приоритета)

1. **MCP `miro`** (`https://mcp.miro.com/`, OAuth, user-конфиг `~/.claude.json`). Рабочие инструменты: `layout_get_dsl` (спека DSL, один раз за сессию) → `board_create` → `layout_create` / `layout_read` / `layout_update`. Проверка: `claude mcp list`.
2. **REST API v2 (запасной, живёт всегда)** — токен `MIRO_TOKEN` в `~/.config/second-brain/miro.env`. База `https://api.miro.com/v2/boards/{board_id}/…`, board_id из URL борда с `%3D` вместо `=`. Ходить **через curl** (питоновский urllib на маке падает по SSL-сертификатам).

**Когда переключаться на REST:** ошибка MCP «This tool is not yet available to your organization / staged rollout» — это серверный фичефлаг Miro, ретраи бесполезны. `board_list_items` при этом может работать — им можно читать.

## 1. Пайплайн создания борда

### Шаг 1: контент сначала в vault
Борд — визуализация, не источник истины. Сначала структурированный markdown-файл в vault (по naming convention), потом борд. Каждый раздел файла = будущий фрейм. В файл после сборки — ссылка на борд; при правках синхронизировать оба.

### Шаг 2: выбрать визуальный формат под задачу
- **Процесс с ролями и AI** → service blueprint: горизонтальные дорожки (lanes) × этапы-колонки. Канонические дорожки: Клиент → Люди → AI-агенты → Боль → Эффект, между «клиентом» и внутренними — «линия видимости» (тонкая серая полоса с подписью).
- **Архитектура / стек** → слои сверху вниз (кто говорит с кем), оркестратор — визуальный центр, связи стрелками с подписями.
- **Roadmap / этапность** → цепочка блоков со стрелками слева направо.
- Один фрейм = одна идея. Фреймы нумеровать («01 · …», «02 · …») — борд читается как история сверху вниз.

### Шаг 3: дизайн-правила (из гайдов NN/g Service Blueprints + Miro Diagram Design 101)
- **3–6 дорожек максимум**, ширина колонок и отступы одинаковые по всему борду (единая сетка = «сделано профессионально»).
- **Словарь цветов: не больше 4–5, каждый цвет = одна роль без исключений.** Проверенный набор: графит #2D2D2D структура/люди · синий #4262FF AI/автоматизация · оранжевый #F2994A боль as-is · зелёный #27AE60 эффект/to-be · красный #EB5757 риск/граница. Зафиксировать легенду на обложке.
- **Шрифт: рабочий размер 24, минимум 18.** Мелкий кегль (13–16) нечитаем на показе — проверено на живом фидбэке. Текст в плашках — по центру (`align=center valign=middle`).
- **Шейпы, не стикеры**, если борд для показа наружу: у shape точные hex-цвета и рамки, у стикеров — ограниченная палитра и «черновой» вид.
- Читаемость проверять на 20–25% зума: если разваливается — борд не готов.
- Стрелки подписывать (caption), связи по смыслу красить в цвет источника.

### Шаг 4: сборка
1. `layout_get_dsl` — один раз, спека в контексте.
2. `board_create` (имя ≤60 символов) — только с подтверждения пользователя.
3. Спланировать геометрию заранее: координаты детей — от **top-left угла фрейма**, центр элемента должен попадать в границы фрейма (иначе падает весь батч). Держать запас по краям ~100px.
4. Один `layout_create` со всеми фреймами и элементами; коннекторы в конце того же DSL (ссылаются на алиасы).

### Шаг 5: верификация (обязательно, result_dsl врёт)
- `board_list_items` (или REST `GET /items` с пагинацией) → посчитать элементы по фреймам против плана, проверить дубли по текстам.
- **Не верить отчёту `layout_create` о failed/created** — сервер путает ID и статусы. Истина только в фактическом чтении борда.
- После верификации — ссылку на борд в vault-файл и в трекер задачи.

## 2. Пайплайн правок

- Точечные правки: `layout_update` = find-and-replace по DSL. Подстрока (`"Бриф-бот" → "Бриф-агент"`, `replace_all`) — для переименований; полная строка → пустая замена — для удаления; правка полной строки — для геометрии/стилей.
- Перед заменой полных строк — свежий `layout_read` нужного фрейма: DSL нормализуется (lowercase hex, fill_opacity и т.д.), старые echo не совпадут.
- **Пользователь может править борд руками параллельно** — не перезаписывать его правки: перед структурными изменениями перечитать состояние; новые крупные блоки добавлять отдельным фреймом рядом, а не пересборкой существующего.
- Сдвиг фреймов: у фрейма меняется центр (x/y в строке FRAME) — дети едут вместе с ним (координаты относительные).
- REST-правки: `PATCH /shapes/{id}` (`style.fontSize`, `style.textAlign`, `data.content`), `PATCH /texts/{id}`. Массовые проходы — скриптом с паузой ~0.1с между запросами.

## 3. Известные грабли Miro API

1. **Атомарные чанки по 20**: bulk-create валится целиком, если невалиден хоть один элемент. Частая причина — SHAPE с высотой < ~12px (тонкие линии делать h=12).
2. **Сервер врёт при частичном сбое**: result_dsl и failed_items могут показывать чужие ID. После любого сбоя — фактическая сверка и ручная зачистка дублей (`layout_update` с пустой заменой).
3. **`parent=` со ссылкой на существующий фрейм по URL может падать (HTTP 400)** — вместо этого таргетить фрейм через `?moveToWidget=<frame_id>` в miro_url и не указывать parent.
4. **Коннекторы с алиасами** работают только на элементы из того же DSL; на существующие — полные URL элементов.
5. **TEXT-элементы, созданные через MCP, могут не патчиться по REST** (internal error 3.0000) — лечится пересозданием: `POST /texts` с теми же content/position/parent → `DELETE` старого.
6. MCP-инструменты `layout_*` могут отвалиться фичефлагом посреди сессии — см. секцию 0, переключение на REST.

## 4. Ограничения

- `board_create` и структурные пересборки — с подтверждения Антона; его ручные правки на борде не перезаписывать.
- Устаревшие борды не удалять — пометить «(устарел, можно удалить)» в vault, удаляет Антон.
- Контент борда всегда зеркалить в vault-файл (источник истины — файл).
- Секреты (MIRO_TOKEN) — только в `~/.config/second-brain/`, не в vault.
