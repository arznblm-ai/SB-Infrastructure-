# Model Pipeline — конвейер план → архитектура → исполнение

Источник паттерна: reels sam.aibuilds (2026-07-01) и kayvon.ai (2026-07-02) — заметки в `transcripts/external resources/`.
Принцип: **дорогая модель не читает кодовую базу и не пишет код.** Она читает карту и план, принимает архитектурные решения и дирижирует дешёвыми исполнителями.

Конвейер инструмент-агностичен: он описывает **стадии**, а не инструменты. Кто физически выполняет стадию execution — Claude-субагент, внешний CLI или что-то следующее — решает `route/SKILL.md` по реестру исполнителей и health-check в момент вызова. В этом файле исполнитель называется исполнителем; конкретные имена, шаблоны вызова и их грабли живут только в реестре `route`.

## Когда включаться

- Автоматически: любой implementation-intent в код-проекте. Порог низкий: **любая новая функция, новый файл, новый скрипт, HTML — конвейер, даже если это «один файл»**. Код-проекты — это и `projects/*`, и скрипты инфраструктуры (`infrastructure/*/Scripts/` и аналогичные каталоги: Krisp, daily focus, боты, exporters).
- Вторая фаза debug-сессий: диагноз поставлен → фикс кода >5 строк идёт через конвейер (обычно сразу Стадия 3, план не нужен — диагноз и есть спецификация).
- НЕ включаться: правка ≤5 строк в одном существующем файле (typo, path, константа, флаг — сделай напрямую), чистая диагностика/eval без правок, чистый research, работа с .md-заметками vault.

## Роли моделей

| Стадия | Кто | Почему |
|--------|-----|--------|
| План / раскопки контекста | дешёвый субагент (`Agent`, `model: sonnet`) | дёшево; болтовня и чтение — самая объёмная часть |
| Архитектура | главная сессия | мало токенов, максимум качества решений |
| Execution | **исполнитель по `route`** — реестр + health-check в момент вызова | руки не должны стоить как мозг; конкретный инструмент подменяем |
| Verify (тесты, запуск) | тот же исполнитель, что делал задачу | у него уже есть контекст и рабочий каталог |
| Обновление карты | дешёвый субагент | механическая работа |

## Выбор исполнителя

Кто именно исполняет — **не решается в этом файле**. Правило выбора, реестр инструментов, health-check, форс-фразы Антона и фолбэк живут в `route/SKILL.md`. Здесь — только то, что зависит от типа работы, а не от инструмента:

1. **Правки `.md`-заметок vault** — не execution: пишет главная сессия сама или дешёвый субагент. Внешним исполнителям заметки vault не отдаём.
2. **Код всегда лежит в валидном рабочем каталоге:** `projects/*`, `infrastructure/<проект>/`, `tasks/<задача>/`. Кросс-проектная задача — несколько последовательных вызовов с разными каталогами, а не один вызов с корнем vault.
3. **Широкий веер мелких независимых правок** (>3 каталога, каждая ≤5 строк) — несколько вызовов с разными каталогами, параллельно или последовательно.
4. **Правки ≤5 строк в одном существующем файле** — напрямую главной сессией, без конвейера: один субагент дороже правки.
5. Любая новая функция, новый файл, скрипт или HTML — конвейер, даже если это «один файл». «Так быстрее», «так проще», «задача маленькая» — не основания писать код в главной сессии.

Исполнитель называется вслух в отчёте (правило 4 в `route`): «сделано» без имени исполнителя — неполный отчёт.

## Workflow

### Стадия 0 — Подхват готового плана

1. Определи проект и его корень (например `projects/Spot Films/`).
2. Проверь `tasks/<проект>/` и корень проекта на свежий план-файл `{*} {plan} <фича> – YYYY-MM-DD.md`, совпадающий по теме.
3. Есть план (например, Антон набросал его с телефона в чате с Sonnet) → **сразу Стадия 2**. Нет — Стадия 1.

### Стадия 1 — План (дёшево)

1. Главная сессия задаёт Антону точечные вопросы, только если без них план будет неправильным. Задача большая и scope неясен — это не вопросы, а грилинг: `/grill` (заменил Context Confidence Gate, ADR-014), его выход и есть план-файл.
2. Запусти **Sonnet-субагента** (`Agent`, `model: sonnet`): дай ему бриф Антона + путь к проекту + `ARCHITECTURE.md`. Задача субагента: докопать контекст (читать файлы можно ему, не главной сессии) и записать план-файл в `tasks/<проект>/` по конвенции имён:
   - цель и expected output;
   - задачи списком с зависимостями;
   - у каждой задачи пометка: `human` / `agent`;
   - что out of scope.
3. Главная сессия план не пересобирает — только проверяет на здравость.

### Стадия 2 — Архитектура (главная модель, минимум токенов)

1. Прочитай **только**: план-файл + `ARCHITECTURE.md` корня проекта. Точечно — отдельные файлы, если карта указывает на риск. **Не сканируй кодовую базу.**
2. Нет `ARCHITECTURE.md` или он старше значимых изменений → сначала сгенерируй его Sonnet-субагентом (контракт ниже).
3. Выдай архитектурное решение и допиши его секцией `## Architecture` в план-файл: какие файлы менять, какие интерфейсы/контракты, порядок задач, что распараллеливается.
4. Если архитектура меняет scope плана — предложениям главной модели приоритет (как в рилсе), но изменение scope озвучь Антону.

### Стадия 3 — Execution (руки: исполнитель по `route`)

1. На каждую задачу плана — один вызов исполнителя (кого и как — `route/SKILL.md`). Спецификация по единому формату из `route`: цель, точные пути файлов, релевантный кусок `## Architecture`, запреты, требование краткого отчёта. Не давай исполнителю «весь проект».
2. Независимые задачи по разным файлам — параллельно; зависимые — последовательно, с сохранением контекста исполнителя, если его адаптер это умеет.
3. Результат каждого исполнителя главная сессия проверяет **по краткому отчёту**, не перечитывая diff целиком. Полный diff — только точечно: файлы с риском по отчёту или упавшие тесты. Лимит — 2 ревью-итерации на задачу, дальше отчёт Антону с вариантами.
4. **Исполнитель короткоживущий (правило 2026-08-04).** Один субагент = одна задача с её ≤2 ревью-итерациями, затем закрыть. Не гонять одного исполнителя сотнями сообщений через SendMessage: каждый его ход заново перечитывает весь накопленный контекст (кейс 03.08 — один исполнитель-субагент на 870 сообщений, ~305 млн cache-read токенов). Следующая задача или затянувшаяся итерация — свежий субагент, которому передаётся компактная спецификация текущего состояния (что сделано, что сломано, что делать), а не история диалога.

### Стадия 4 — Verify и закрытие

1. Прогони проверку (тесты / запуск приложения / smoke-check) — вторым вызовом того же исполнителя, не локальным Bash в главной сессии; главная сессия читает только вердикт pass/fail + короткий хвост лога.
2. Обнови статусы задач в план-файле.
3. Если менялась структура кода — обнови `ARCHITECTURE.md` (дешёвый субагент).
4. Отчёт Антону: что сделано, как проверено, что осталось на `human`-задачах.

## Контракт ARCHITECTURE.md

Лежит в корне код-проекта. Секции:

1. **Module map** — каждый каталог/entry-файл одной строкой.
2. **Data flows** — ключевые сценарии от входа до выхода.
3. **Key decisions** — кэширование, БД, очереди, внешние API, вызовы LLM (с model id).
4. **Conventions** — конфиг, промпты, шаблоны, env.
5. Футер: `Generated: YYYY-MM-DD` + правило «обновлять после структурных изменений».

Правило для всех агентов проекта: **сначала карта, файлы — только точечно.**

## Token discipline (жёсткие правила)

- Главная сессия НЕ читает кодовую базу целиком и НЕ пишет код руками.
- **Самопроверка перед любым Edit/Write кода главной сессией:** «это ≤5 строк в одном существующем файле?» Нет — стоп, вызов исполнителя. Это касается и скриптов инфраструктуры, и HTML, и «быстрых фиксов» после отладки.
- Выходы исполнителей ревьюятся по краткому отчёту, не по полному diff (Стадия 3 здесь; требования к отчёту — контракт исполнителя в `route/SKILL.md`).
- **Debug-петля:** >10 Bash-вызовов подряд по одной проблеме в главной сессии = нарушение — стоп, спецификация исполнителю (правило в Router Rules корневого CLAUDE.md). Главная сессия не чинит код итерациями «запустил → поправил → запустил».
- **Исполнители короткоживущие:** одна задача + ≤2 ревью-итерации на субагента, дальше свежий субагент с компактной спецификацией состояния (Стадия 3, п. 4). Марафонский диалог с одним исполнителем — главная статья расхода cache-токенов.
- Субагенты получают точные пути, а не «разберись в проекте».
- Планы переиспользуются между сессиями: новая сессия начинает с план-файла, не с раскопок.
- Если задача ≤5 строк — конвейер не разворачивать, сделать напрямую (дешевле одного субагента).

## Confirmation gates

- Изменение scope, удаление файлов, миграции БД, внешние отправки — только с явного подтверждения Антона.
- `human`-задачи из плана агенты не выполняют — оставляют Антону.
