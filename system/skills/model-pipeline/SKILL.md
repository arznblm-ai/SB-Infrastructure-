# Model Pipeline — конвейер Sonnet → Fable → GPT

Источник паттерна: reels sam.aibuilds (2026-07-01) и kayvon.ai (2026-07-02) — заметки в `transcripts/external resources/`.
Принцип: **дорогая модель не читает кодовую базу и не пишет код.** Она читает карту и план, принимает архитектурные решения и дирижирует дешёвыми исполнителями.

> **Обновление 2026-07-13:** Opus исключён из конвейера (решение Антона). Связка — Fable (архитектура + ревью) и GPT 5.6 через Codex CLI (единственный исполнитель, скилл `route`): код пишется на квоте ChatGPT-подписки, лимиты Claude тратятся только на мышление. Codex недоступен → стоп и сообщить Антону; Opus — только по явной команде «на опусе». Мозг конвейера всегда — главная сессия (Fable).

## Когда включаться

- Автоматически: любой implementation-intent в код-проекте. Порог низкий: **любая новая функция, новый файл, новый скрипт, HTML — конвейер, даже если это «один файл»**. Код-проекты — это и `projects/*`, и скрипты инфраструктуры (`infrastructure/*/Scripts/` и аналогичные каталоги: Krisp, daily focus, боты, exporters).
- Вторая фаза debug-сессий: диагноз поставлен → фикс кода >5 строк идёт через конвейер (обычно сразу Стадия 3, план не нужен — диагноз и есть спецификация).
- НЕ включаться: правка ≤5 строк в одном существующем файле (typo, path, константа, флаг — сделай напрямую), чистая диагностика/eval без правок, чистый research, работа с .md-заметками vault.

## Роли моделей

| Стадия | Кто | Почему |
|--------|-----|--------|
| План / раскопки контекста | Sonnet-субагент (`Agent`, `model: sonnet`) | дёшево; болтовня и чтение — самая объёмная часть |
| Архитектура | Главная сессия (Fable / лучшая доступная) | мало токенов, максимум качества решений |
| Execution | GPT 5.6 через Codex CLI — единственный исполнитель (шаблоны вызова — `route/SKILL.md`) | код пишется на квоте ChatGPT, лимиты Claude не тратятся |
| Execution при недоступном Codex | нет — стоп + сообщить Антону; Opus только по явной команде | Opus исключён из схемы (2026-07-13) |
| Обновление карты | Sonnet-субагент | механическая работа |

## Выбор исполнителя (правило, 2026-07-13)

**GPT 5.6 (Codex CLI) — единственный исполнитель.** Каждая execution-задача уходит в `codex exec` по шаблонам из `route/SKILL.md`. Opus-субагенты исключены из конвейера — исполнение никогда не возвращается в Claude молча.

Крайние случаи:
1. **Codex недоступен** (бинарник пропал, ошибка auth, квота GPT исчерпана — 5-часовое или недельное окно) → сообщить Антону и остановиться. Не исполнять на Opus без его явного решения;
2. **правятся .md-заметки vault** — это не код и не execution: пишет Fable сам (работа мозга) или Sonnet-субагент. Codex в .md-заметки не пускаем. Код же почти всегда лежит в валидном `-C`-каталоге: `projects/*`, `infrastructure/<проект>/` (Scripts и рядом), `tasks/<задача>/`. Кросс-проектный код — несколько последовательных `codex exec` с разными `-C`;
3. **широкий веер мелких независимых правок** (в >3 каталогах, каждая ≤5 строк) — несколько `codex exec` с разными `-C`, параллельно или последовательно;
4. **«на опусе» / «без джипити» от Антона** — единственный путь к Opus-субагентам.

«Так быстрее», «так проще», «задача маленькая» — не основания исполнять в Claude: маленькая задача либо ≤5 строк (тогда напрямую), либо уходит в Codex.

Форс: «через джипити», «route» — всегда GPT, без раздумий. Напрямую главной сессией, без конвейера и исполнителей — только правки ≤5 строк в одном существующем файле (typo, path, константа, флаг). Любая новая функция, новый файл, скрипт или HTML — Codex, даже в «одном файле».

## Workflow

### Стадия 0 — Подхват готового плана

1. Определи проект и его корень (например `projects/Spot Films/`).
2. Проверь `tasks/<проект>/` и корень проекта на свежий план-файл `{*} {plan} <фича> – YYYY-MM-DD.md`, совпадающий по теме.
3. Есть план (например, Антон набросал его с телефона в чате с Sonnet) → **сразу Стадия 2**. Нет — Стадия 1.

### Стадия 1 — План (дёшево)

1. Главная сессия задаёт Антону 3–5 точечных вопросов (Context Confidence Gate из корневого claude.md), только если без них план будет неправильным.
2. Запусти **Sonnet-субагента** (`Agent`, `model: sonnet`): дай ему бриф Антона + путь к проекту + `ARCHITECTURE.md`. Задача субагента: докопать контекст (читать файлы можно ему, не главной сессии) и записать план-файл в `tasks/<проект>/` по конвенции имён:
   - цель и expected output;
   - задачи списком с зависимостями;
   - у каждой задачи пометка: `human` / `agent`;
   - что out of scope.
3. Главная сессия план не пересобирает — только проверяет на здравость.

### Стадия 2 — Архитектура (главная модель, минимум токенов)

1. Прочитай **только**: план-файл + `ARCHITECTURE.md` корня проекта. Точечно — отдельные файлы, если карта указывает на риск. **Не сканируй кодовую базу.**
2. Нет `ARCHITECTURE.md` или он старше значимых изменений → сначала сгенерируй его Sonnet-субагентом (контракт ниже).
3. Выдай архитектурное решение и допиши его секцией `## Architecture` в план-файл: какие файлы менять, какие интерфейсы/контракты, порядок задач, что распараллеливается.
4. Если архитектура меняет scope плана — предложениям главной модели приоритет (как в рилсе), но изменение scope озвучь Антону.

### Стадия 3 — Execution (руки: GPT 5.6)

1. На каждую задачу плана — `codex exec` по шаблонам из `route/SKILL.md`. В спецификацию: задача + релевантный кусок `## Architecture` + точные пути файлов + требование краткого отчёта (что изменил, файлы, как проверил, риски). Не давай исполнителю «весь проект».
2. Независимые задачи по разным файлам — параллельно; зависимые — последовательно (для Codex — `exec resume --last`).
3. Результат каждого исполнителя главная сессия проверяет **по краткому отчёту**, не перечитывая diff целиком. Полный diff — только точечно: файлы с риском по отчёту или упавшие тесты. Лимит — 2 ревью-итерации на задачу, дальше отчёт Антону с вариантами.

### Стадия 4 — Verify и закрытие

1. Прогони проверку (тесты / запуск приложения / smoke-check) — вторым `codex exec` / `exec resume`; Fable читает только вердикт pass/fail + короткий хвост лога.
2. Обнови статусы задач в план-файле.
3. Если менялась структура кода — обнови `ARCHITECTURE.md` (Sonnet-субагент).
4. Отчёт Антону: что сделано, как проверено, что осталось на `human`-задачах.

## Контракт ARCHITECTURE.md

Лежит в корне код-проекта. Секции:

1. **Module map** — каждый каталог/entry-файл одной строкой.
2. **Data flows** — ключевые сценарии от входа до выхода.
3. **Key decisions** — кэширование, БД, очереди, внешние API, вызовы LLM (с model id).
4. **Conventions** — конфиг, промпты, шаблоны, env.
5. Футер: `Generated: YYYY-MM-DD` + правило «обновлять после структурных изменений».

Правило для всех агентов проекта: **сначала карта, файлы — только точечно.**

## Token discipline (жёсткие правила)

- Главная сессия НЕ читает кодовую базу целиком и НЕ пишет код руками.
- **Самопроверка перед любым Edit/Write кода главной сессией:** «это ≤5 строк в одном существующем файле?» Нет — стоп, `codex exec`. Это касается и скриптов инфраструктуры, и HTML, и «быстрых фиксов» после отладки.
- Выходы исполнителей ревьюятся по краткому отчёту, не по полному diff (см. Стадия 3 и `route/SKILL.md` Стадия 3).
- Субагенты получают точные пути, а не «разберись в проекте».
- Планы переиспользуются между сессиями: новая сессия начинает с план-файла, не с раскопок.
- Если задача ≤5 строк — конвейер не разворачивать, сделать напрямую (дешевле одного субагента).

## Confirmation gates

- Изменение scope, удаление файлов, миграции БД, внешние отправки — только с явного подтверждения Антона.
- `human`-задачи из плана агенты не выполняют — оставляют Антону.
